R-02

Upload 835

ModalMVP
Purpose
Bring in remittance files that do not arrive automatically, and check what is in them before importing.
Data
Uploaded file (835 X12 or a PM export); parse result: payer, payments, trace numbers, totals, claims count, client match by payee NPI or tax ID; duplicate check on payer + trace + amount + date.
Actions
Drop or browse files (several at once); review the parse summary; untick a payment to skip it; Import.
States
Step 1: drop zone. Step 2: summary (shown). Parse error: the file name, line and segment where it failed, and "Nothing was imported". Duplicate: the payment row is unticked and labeled "Already imported Oct 27".
Rules
Raw file is stored encrypted before parsing. Import is idempotent; duplicates are recorded and ignored. Payments whose payee does not match a client cannot be imported.

R-03

Remittance detail: posting (Mode B)

PageMVPRoute /remittances/:id
Purpose
Show a payment Cleanpost received from Stedi and how each claim in it was posted into the PM.
Data
remittances header; balance check (BPR payment = sum of CLP paid − PLB); remit_claims with remit_lines, remit_adjustments (group + CARC) mapped through adjustment_mappings to PM codes, remit_remarks; postings per claim (status, method, attempts, last_error).
Actions
  • Expand a claim to see its lines and adjustments with the PM code each maps to.
  • Post now (retries pending or failed claims); Send to manual (creates M-01).
  • Code chips open R-08. Claim link opens C-02.
  • View raw 835 (admin, audit-logged).
States
Posting in progress: per-claim spinner chip "Posting". Partial failure: R-09 banner. Denied line: posted with balance left open, chip "Denial worked separately".
Rules
Nothing posts unless the 835 balances. Post now asks for confirmation (G-11) because it writes to the PM. Every posting attempt is audited with method (API, file, browser, manual).

R-04

Remittance detail: verification (Modes A and C)

PageMVPRoute /remittances/:id
Purpose
Check that what the PM posted automatically matches the 835, line by line, and work the differences.
Data
Parsed 835 (from the PM via pullRemittances, or uploaded; always uploaded for Tebra, whose API has no remittance files); PM postings via pullPostings; per-line comparison: paid, each adjustment translated to the PM code, patient responsibility; unmatched remit_claims.
Actions
  • Show differences first (default on).
  • Per difference: Correct in PM (adapter or manual task), Accept PM posting with reason, Create posting task when nothing was posted.
  • Unmatched claim: Link to claim (R-05) or Mark as before go-live.
States
All lines match: green banner "Verified" and the table collapses to a summary. PM has not posted yet: lines show "Waiting for PM" with the next sync time; becomes a difference after 2 syncs. PM postings without adjustment codes (possible for Tebra; confirm in the Tebra test): the comparison checks amounts per line and shows "Code not available from Tebra" in place of the PM code.
Rules
Cleanpost never posts in Modes A and C. Two separate checks, labeled separately: "835 balances" (before) and "PM posting matches" (after). Differences auto-resolve when a later sync matches.

Data

Manual tasks

When a client's PM has no integration for an operation, Cleanpost prepares the work with every value filled in and a biller completes it in the PM. This is what lets a client go live before any integration exists.

M-01

Manual task

PageMVPRoute /tasks/:id
Purpose
Let a biller complete an operation in the PM by hand, quickly and without mistakes.
Data
manual_tasks (operation, connection, payload_ref); for postings: remittance header, balance check, allocations per claim and line with amounts and adjustment names already mapped to the client's PM codes; PM-specific instructions where known.
Actions
  • Copy buttons beside each value.
  • Tick rows as entered (kept per user while the task is open).
  • Download worksheet as CSV or PDF (F-02).
  • Mark as posted, with the PM's payment ID (required).
  • I couldn't complete this (M-02).
States
Started by another user: banner with their name and time. Completed: read-only with who, when and the PM reference. A later sync that verifies the posting marks it verified.
Rules
Marking as posted records the actor and PM reference, resolves the work item, and, if the PM can be read, schedules verification. Worksheet downloads are audit-logged.
